How AadiCrypto is put together

Home and News look like one page. Underneath they are three different kinds of data moving at three different speeds. This is how they fit together, and the rules that keep the site fast, cheap and safe as traffic grows.

Frontend Next.js (SSR + ISR) API Node, read-only JSON Store PostgreSQL + Redis Host Hostinger VPS + Cloudflare

01 — The shape of the problem

Three kinds of data, one page

The top strip on every page carries live market numbers. The middle of the page carries stories. The nav, footer and Learn pages barely change at all. They arrive on the same screen, so it is tempting to treat them the same way. Don't.

If the whole page waits for live prices, every news article becomes slow, and slow news pages don't rank. Split them at the start and each one gets the cache it deserves.

KindWhere it showsChangesHow it is served
Market data Top ticker, price widgets, the whole /markets tree ~10 sec One worker fetches, everyone reads the same cached copy
News Hero story, Latest News rail, topic blocks, Most Read ~5 min Stored in your database, cached hard, cleared on publish
Editorial furniture Nav, footer, newsletter block, Learn pages rarely Built into the page, cached for hours
Each row wants a different cache lifetime. One cache setting for all three is the most common way a crypto site ends up slow.

02 — The first decision

Render the pages on the server

Today the site is a plain React app: the browser downloads JavaScript, then draws the page. For an app behind a login that is fine. For a news site that lives on search traffic, it quietly costs you most of your audience.

A crawler asking for an article gets an empty shell. There is no headline in the HTML, no description, no social preview image. Google will sometimes come back later and run the JavaScript, but that pass is delayed and not guaranteed — and Google News works on a timescale of minutes, not days.

Decision 01

Move the frontend to Next.js with the App Router. Same React components, same design, but the HTML is built on the server. Do this before wiring in real data, not after — retrofitting it later means touching every page.

The same move pays for itself in three other places: a sitemap.xml plus a proper news sitemap, an RSS feed, and NewsArticle structured data on every story. None of those are extras for a publisher. They are how the traffic arrives.

03 — The stack

How a price and a story reach the page

Data moves in one direction. Sources on the left, readers on the right, and nothing skips a step. The two stores in the middle are what make the right-hand side cheap.

04 — The rule that keeps it cheap

The browser never calls a third-party API

One worker fetches prices every ten seconds and writes them to Redis. The API reads Redis. Nothing else touches the upstream.

So whether you have a hundred readers or a hundred thousand, you still make about six upstream calls a minute. Your bill stays flat, your keys stay secret, and you are never rate-limited during the exact market crash that brings you traffic.

Calling a price API straight from React looks easier for about a week. Then three things happen at once: the key is sitting in your JavaScript bundle where anyone can read it, the provider starts throttling you because ten thousand browsers are each asking separately, and you have no way to cache a response you never controlled.

The same rule applies to news. A worker pulls the feeds on a schedule, cleans them up and stores them. Pages read your database, never someone else's server.

Everywhere you cache, use stale-while-revalidate: if the upstream is slow or down, readers get slightly old data instead of a blank box. For a news site that trade is always worth it.

05 — Layer by layer

What each piece is responsible for

Five moving parts. Each one has a single job, and each can be replaced without touching the others.

  1. 01 — INGESTION WORKERS

    Fetch, clean, and hand over

    A separate process from the API, so a stuck feed can never take the website down. The price worker runs every 10 seconds, the news worker every 2–5 minutes.

    Each source gets its own small adapter file that converts that provider's shape into your shape. Swapping CoinGecko for CoinMarketCap should mean editing one file, not fifty. News gets deduplicated by URL hash plus a loose title match, because the same story arrives from five feeds. Failed fetches retry with backoff; if a source dies, log it and keep serving the last good copy.

  2. 02 — STORAGE

    Postgres is the truth, Redis is the speed

    PostgreSQL holds articles, topics, coins, authors, sources and tags — anything you would be upset to lose. Redis holds the live market snapshot, cached API responses and rate-limit counters, and is never the only copy of anything.

  3. 03 — THE API

    One read-only public surface

    Versioned under /api/v1, JSON only, no writes from the public internet. Every response carries its own Cache-Control header so Cloudflare does most of the work before a request ever reaches your server.

  4. 04 — THE FRONTEND

    Mostly pre-built, live only where it matters

    Home and the news list use ISR — the page quietly rebuilds itself every 60 seconds in the background, so readers always hit a ready file. Article pages do the same, and get rebuilt on demand the moment an editor publishes. The top ticker is the one piece that polls from the browser, and it polls your own API.

  5. 05 — THE EDGE

    Cloudflare in front of everything

    The free tier is enough. It absorbs the repeat traffic, hides your server's real IP address, and gives you TLS, bot filtering and basic DDoS protection without adding a line of code. This is what lets a small VPS serve a large audience.

07 — Security

The things that actually go wrong

Nothing exotic here. Almost every incident on a site like this comes from one of these ten rows.

AreaWhat to do
API keysServer-side environment variables only. Never a NEXT_PUBLIC_ or VITE_ variable — those get baked into the JavaScript bundle and anyone can read them.
DatabaseBound to localhost or a private network. Never a public port. Strong password, and a separate read-only user for the API.
Server accessSSH keys only, password login disabled, non-root user, fail2ban. Firewall open on 443 and your SSH port, nothing else.
Origin exposureCloudflare proxy on, so your Hostinger IP is never public and nobody can go around the edge.
Rate limitingPer-IP limits on the API, in Nginx or middleware. Stops scrapers from turning your API bill into their free data feed.
CORSLocked to your own domain. A read-only API is not a reason to leave it open.
InputValidate every query parameter with a schema. Parameterised SQL everywhere, no string building.
Feed contentSanitise HTML pulled from RSS before you store it. Feeds can carry scripts, and this is a real XSS route into your own pages.
Admin panelIts own subdomain, behind login plus two-factor, ideally IP-restricted. Never share a session with the public site.
BackupsNightly Postgres dump to storage that is not the same server. Restore it once, on purpose, before you need to.

08 — Hosting

Running it on Hostinger

Use a VPS, not shared hosting. Shared plans are built for PHP and cannot reliably keep a Node process, a background worker, Redis and Postgres alive. A KVM 2 is a comfortable starting point.

Everything runs as containers from a single docker-compose.yml, which means rebuilding the whole stack on a fresh machine takes about ten minutes. That file is also your disaster-recovery plan.

ContainerJob
nginxReverse proxy, TLS, compression, per-IP rate limits
webNext.js — renders the pages
apiThe read-only JSON API
workerPrice and news ingestion on a schedule
postgresArticles, topics, coins, authors
redisLive snapshot, response cache, rate-limit counters

Deploys run from GitHub Actions: build the images, SSH in, docker compose pull && up -d. Keep a staging stack on the same box with its own database so you can test a feed change without breaking the live site.

When traffic grows, nothing here gets rewritten. The API is stateless, so you run two or three copies behind Nginx. Then a Postgres read replica. Then the workers move to their own small box. That is the whole scale path.

09 — Code layout

One repository, clear seams

aadicrypto/
├── apps/
│   ├── web/          Next.js — the site you already designed
│   ├── api/          public read-only API
│   └── worker/       scheduled ingestion jobs
├── packages/
│   ├── types/        shared TypeScript types — one contract, both sides
│   ├── db/           schema + migrations
│   └── adapters/     one file per data provider
├── docker-compose.yml
└── .github/workflows/

The packages/types folder matters more than it looks. When the API and the frontend share one set of types, a breaking change fails at build time instead of showing up as a blank widget on the live home page.

And packages/adapters is where every third-party quirk is allowed to live. Everything past that line speaks your schema and nobody else's.

10 — Still open

Decisions that change the build

The architecture above holds either way on all of these, but the sizing and the data sources depend on the answers.

  • Traffic. Hundreds a day or tens of thousands? Changes the VPS size and nothing else.
  • Where the news comes from. Written in-house, pulled from feeds, or both? Pure aggregation has copyright limits; a mix is usually the safest place to land.
  • Which Hostinger plan is already bought. If it is shared hosting, the frontend and the API have to be split across two places.
  • How India-focused the site is. The site already has an India section and INR pricing, which changes both the price source and the feed list.
  • Whether editors need an admin panel, or the whole thing runs automatically.
